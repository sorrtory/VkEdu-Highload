# 3. Глобальная балансировка нагрузки

Самая тяжелая часть этого приложения это лента.
Поэтому для пользователей мы создаем inbox,
куда будем класть скелеты постов заранее и не мучить базу при каждом запросе (fanout on write).
Этот inbox будет содержать различные id, ссылки на медиафайлы и другую метаинформацию, а
текст поста будет отдаваться по запросу из кешей ЦОД или прямиком базы.

Алгоритм формирования inbox будет основополагающим и должен улучшаться бесконечно.
Если вкратце, мы будем в зависимости от активности пользователя брать его
подписки и рекомендации (популярные посты ~~подписки людей с похожими интересами~~).
Для активных пользователей можно собирать сотни постов, а для менее активных - десятки или меньше.
Триггером будет служить публикация нового поста сообществом
и запрос новых постов в ленте пользователем (здесь будет нужна хорошая очередь, чтобы не положить систему).
Для популярных сообществ (например, 100к+ подписчиков) посты можно сразу прогревать в CDN как популярные,
либо раскидывать постепенно+выборочно.

Так, при открытии ленты:

- Клиент запрашивает с API посты
- API определяет домашний регион пользователя
- API достает скелеты постов пользователя из его inbox
- API собирает тексты, лайки, комментарии постов из базы или кеша и отдает клиенту
- Фронт рисует ленту относительно полученных данных. За медиафайлами ходит на CDN

На 1000 км идет задержка примерно 10 мс.
Мы работаем только по РФ и 70% пользователей находятся в ее европейской части.
Важно обеспечить быструю загрузку контента для европейской части России,
остальные регионы будут терпеть более высокий RTT.
Наше приложение не предполагает рилтайм, поэтому даже 10_000 км ~= 200 мс
RTT для получения поста в ленте не будет непреодолимой преградой.

## Домены

- `vk.ru` - главная страница
- `api.vk.ru` - API сообщений, лайков, комментариев и т.д.
- `media.vk.ru` - внутреннее origin хранилище для CDN
- `login.vk.ru` - авторизация
- `mycdn.me` - CDN для статики, медиафайлов и снапшотов популярных постов

## Размещение датацентров

Датацентры пытаемся размещать в местах с хорошей городской инфраструктурой,
чтобы обеспечить высокую скорость физического доступа, надежность,
низкую цену за электричество и обслуживание.

Три равных датацентра ставим в Петербурге, Москве и Екатеринбурге.
Сервисы делаем независимыми от состояния, запускаемся в кубере.
Базу, и медиафайлы из s3 реплицируем между всеми тремя датацентрами
для общих данных (пользователи, посты, комментарии) и
для важных данных (сообщения, настройки, подписки).

Для ленты будем использовать шардирование по региону.
Так inbox пользователей с Владивостока будет находится в ближайшем ЦОДе в ЕКБ и тп.

На чтение ходим только в ближайшую реплику, пишем только в home region,
общие данные разносим между всеми тремя датацентрами, при необходимости можно
использовать кворум

В датацентрах закладываем избыточность.
Имея 33%+33%+34% инфраструктуры на [300к RPS](./02.md#rps),
мы хотим позволить себе потерять один датацентр и продолжать работу без деградации.
То есть каждый датацентр в идеале держит пик на 100к RPS с запасом.

В целях экономии имеем не чистый N+1 на 150к, а, пожалуй, где-то 125к RPS на датацентр.
В случае падения одного датацентра, будем иметь механизм деградации ленты.
Будем пытаться раздавать ленту преимущественно из CDN, inbox будем обновлять с задержкой.

Уточню, что большая часть RPS идет из текстового месседжера,
что кушает довольно [мало трафика](./02.md#сетевой-трафик).
Так что при высокой нагрузке, имеет смысл начать с деградации ленты/рекомендаций и держаться
за мессенджер до конца.

Поэтому даже при падении одного датацентра, мы будем продолжать обслуживать пользователей,
пусть и с некоторой деградацией ленты.

### Балансировка API

Принимаем тот факт, что пользователи с Дальнего Востока пойдут за API в ЕКБ на ~7000 км = 70мс => RTT = 140мс.
Для комментариев и сообщений это не так заметно, а вот медиафайлы и ленту будем отдавать через CDN.

Для балансировки API используем ближайший здоровый датацентр, к примеру, используем Anycast.

Внутри нашего приложения прибиваем каждого пользователя к одному датацентру по хешу (home region).

Заметим, что кеши (в основном тут важен inbox) будут находиться в домашнем регионе пользователя,
поэтому при попадении пользователя в неродной ЦОД, проксирум его запросы туда
(пингуем с таймаутом, иначе формируем новые кешы и ленту с задержкой).,
Тогда при перестройке маршрутов будем подгружать его данные из родного ЦОДа до тех пор,
пока не сформируем новые кеши в новом ЦОДе и пользователь не переедет полностью.
Это не идеально, но BGP не должен так часто прыгать между отдаленными датацентрами.

То есть случае перестройки маршрутов пользователь будет автоматически перенаправлен на другой ЦОД
и потеряет доступ к своему inbox. В целом, для нас это не критично.
Мы сможем грузить посты с CDN, а inbox будем обновляться с задержкой.

Однако в случае падения одного датацентра.
Мы будем вынуждены обработать множество генераций постов на лету.
Для этого используем очередь в каждом датацентре, и реализуем
фронт так чтобы посты грузились по мере их готовности, а не по порядку.

## CDN

Ставим CDN в крупных городах для обеспечения быстрой работы по всей России:
Москва, Волгоград, Екатеринбург, Новосибирск, Хабаровск.

На CDN кладем статику, медиафайлы и популярные посты.
Стараемся всегда при запросе на `api.vk.ru` отдавать ссылку на `mycdn.me`, а не `media.vk.ru`.

CDN будет искать у себя кеши, если их нет - идти на `media.vk.ru` за данными.

Алгоритм определения популярности поста может быть прост:

- популярный паблик - все его посты популярные
- крутой пост, который алгоритм считает хорошей рекомендацией
- пост, который набрал много лайков и комментариев за короткое время

### Балансировка CDN

CDN определяем по Latency-based DNS: ходим туда, где быстрее всего.
