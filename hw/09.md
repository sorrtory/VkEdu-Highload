# 9. Обеспечение надёжности

## Обеспечение надёжности

| Компонент системы       | Метод обеспечения надёжности                                                                                                                                                                                                                                        |
| :---------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| LVS (L4)                | Резервирование Active–Active (N+1) с Keepalived. Виртуальный IP переходит на резервный узел при отказе основного.                                                                                                                                                   |
| Nginx (L7)              | Резервирование Active–Active (N+1). Горизонтальное масштабирование reverse-proxy. Узел исключается из балансировки при ошибках health-check на уровне LVS.                                                                                                          |
| Kubernetes              | Несколько реплик каждого stateless-сервиса. `livenessProbe` перезапускает зависший pod, `readinessProbe` убирает pod, если он не готов принимать traffic. Возможен `PodAntiAffinity` для размещения реплик на разных узлах.                                         |
| API Gateway             | Rate limit через Redis. При недоступности части сервисов возвращает частичный ответ или fallback, если сценарий это допускает.                                                                                                                                      |
| PostgreSQL              | Patroni-кластер локален в primary DC: 1 primary + 2 local replicas. Запись идет только в primary. В другие 2 ДЦ данные реплицируются асинхронно. Чтение может идти с replica, если допустима неактуальность. WAL-архивация используется для Point-in-Time Recovery. |
| ScyllaDB                | Replication Factor = 3, consistency level `LOCAL_QUORUM`. Запись возможна в любом ДЦ. Между ДЦ - eventual consistency. При отказе узла данные доступны с реплик.                                                                                                    |
| Redis                   | Локальный Redis Cluster, master + replica на каждый slot. Redis используется как кеш и TTL-хранилище, не является source of truth. При потере кеша данные восстанавливаются из PostgreSQL / ScyllaDB.                                                               |
| Kafka                   | 3+ broker, replication factor = 3. События подтверждаются через `acks=all`. Consumer commit offset только после успешной обработки. При падении worker продолжает с последнего offset.                                                                              |
| SeaweedFS (S3)          | Репликация объектов между дата-центрами. Запись файлов идет в primary DC, чтение - из локального ДЦ или через CDN. Актуальный `storage_key` хранится в PostgreSQL.                                                                                                  |
| OpenSearch              | 3+ data nodes, replica shards. Индекс обновляется асинхронно из Kafka. При потере индекса его можно пересобрать из PostgreSQL, ScyllaDB и Kafka-событий.                                                                                                            |
| Микросервисы            | Graceful Shutdown: сервис перестает принимать новые запросы, завершает текущие операции, коммитит offsets/транзакции и только потом завершает процесс.                                                                                                              |
| Фоновые worker-сервисы  | Идемпотентная обработка событий. Повторная обработка одного события не должна ломать счетчики, ленты и поисковый индекс.                                                                                                                                            |
| CronJob генерации ленты | Повторяемые задачи. Если запуск пропущен, следующий запуск пересобирает ленту за пропущенный интервал.                                                                                                                                                              |

## Паттерны

| Паттерн              | Где используется                                                                                                                    | Как влияет на схему                                                                                                                                                 |
| :------------------- | :---------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Transactional Outbox | `post-service`, `comment-service`, `reaction-service`, `profile-service`, `community-service`, `messenger-service`, `media-service` | Добавляется таблица `event_outbox`. Сервис пишет бизнес-данные и событие в одной транзакции, затем `outbox-relay` читает `event_outbox` и публикует событие в Kafka |
| CQRS                 | Ленты, inbox, поиск, счетчики                                                                                                       | Основные данные пишутся в canonical tables, а `user_feed_items`, `popular_feed_items`, `user_conversations`, OpenSearch и snapshot-счетчики обновляются асинхронно  |
| SAGA (Choreography)  | Публикация поста с медиа, обновление ленты, счетчиков и поиска                                                                      | Операция разбивается на шаги: загрузка файла, создание metadata, создание поста, публикация событий, обновление read-model. При сбое выполняется компенсация        |

Transactional Outbox у нас работает частично.

- Для PostgreSQL-сущностей он полноценный: бизнес-данные и запись в `event_outbox` сохраняются в одной транзакции.
- Для ScyllaDB-сущностей общей транзакции с PostgreSQL нет, поэтому строгой атомарности между записью данных и событием добиться нельзя. В таких случаях сервис дожидается успешной записи в ScyllaDB с `LOCAL_QUORUM`, затем пишет событие в `event_outbox`; надежность обеспечивается retry и идемпотентностью consumers.

### Пример SAGA: публикация поста с медиа

| Шаг | Действие                                                               | Компенсация при ошибке                         |
| :-- | :--------------------------------------------------------------------- | :--------------------------------------------- |
| 1   | `media-service` загружает файл в SeaweedFS                             | Удалить объект или пометить как orphan         |
| 2   | `media-service` создает запись `file_objects`                          | Пометить `file_objects.status = failed`        |
| 3   | `post-service` создает запись `posts` и `post_attachments`             | Пометить пост как `failed` / `deleted`         |
| 4   | `post-service` пишет событие в `event_outbox`                          | Повторить запись события в той же транзакции   |
| 5   | `outbox-relay` публикует `post.events` в Kafka                         | Повторить публикацию                           |
| 6   | `feed-worker`, `search-indexer`, `counter-worker` обновляют read-model | Повторить обработку события idempotent-логикой |

## Graceful Degradation

| Отказ                                 | Поведение системы                                                                                                                    |
| :------------------------------------ | :----------------------------------------------------------------------------------------------------------------------------------- |
| Redis недоступен                      | Сервис читает данные напрямую из PostgreSQL / ScyllaDB. Увеличивается latency, но основные сценарии продолжают работать.             |
| Redis потерял кеш ленты               | `feed-service` строит холодную ленту из `user_feed_items` в ScyllaDB. Первые страницы снова прогреваются в Redis.                    |
| `user_feed_items` временно недоступна | Пользователь получает холодную fallback-ленту из `popular_feed_items` или постов подписанных сообществ.                              |
| `popular_feed_items` недоступна       | Популярная лента строится из последних постов сообществ или возвращается stale cache из Redis.                                       |
| OpenSearch недоступен                 | Поиск временно недоступен или работает только по точным полям из PostgreSQL: `username`, `slug`. Основные сценарии соцсети работают. |
| Kafka недоступна                      | Сервисы продолжают писать бизнес-данные и события в `event_outbox`. Асинхронные read-model обновятся после восстановления Kafka.     |
| `feed-worker` упал                    | Новые посты временно не попадают в персональную ленту. После рестарта worker продолжает обработку с последнего Kafka offset.         |
| `search-indexer` упал                 | Поиск становится stale. После рестарта indexer дочитывает Kafka и догоняет актуальное состояние.                                     |
| `counter-worker` упал                 | Snapshot-счетчики временно устаревают. Каноничные счетчики остаются в `post_counters` / `community_counters`.                        |
| Primary PostgreSQL недоступен         | Patroni выполняет failover на replica. На время failover операции записи могут быть временно недоступны.                             |
| Secondary DC недоступен               | Трафик уводится в другой ДЦ через BGP/DNS. ScyllaDB и Kafka продолжают работу с доступными репликами.                                |
| SeaweedFS недоступен на чтение        | Медиа читаются через CDN или из другого ДЦ. Если объект не найден, UI показывает placeholder.                                        |
| SeaweedFS недоступен на запись        | Публикация постов с медиа временно недоступна. Текстовые посты и сообщения продолжают работать.                                      |

## Холодная лента

| Сценарий                               | Что делаем                                                                                       |
| :------------------------------------- | :----------------------------------------------------------------------------------------------- |
| Redis cache пустой                     | Читаем первые страницы из `user_feed_items` в ScyllaDB и прогреваем Redis.                       |
| `user_feed_items` еще не сгенерирована | Показываем `popular_feed_items` по региону пользователя.                                         |
| Пользователь новый и нет подписок      | Показываем популярную ленту по `home_region`.                                                    |
| `feed-generator-cronjob` отстал        | Показываем последнюю доступную read-model. Новые элементы появятся после обработки Kafka.        |
| Счетчики в ленте устарели              | Показываем snapshot-счетчики. Точные счетчики догружаются из `post_counters` при открытии поста. |
