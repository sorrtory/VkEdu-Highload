# 4. Локальная балансировка нагрузки

Заметим, что большая часть трафика уходит на CDN [см. 3](./03.md#домены)

Ясно что CDN также будет генерировать трафик на API, но его cache miss
будет генерировать незначительный RPS относительного общего.
Выбрать коэфицент cache miss сложно, так как это зависит от алгоритма ленты.
Вообще [нужно](https://www.flashedgecdn.com/blog/what-is-cache-hit-ratio/#:~:text=but%20in%20general%2C%20anything%20above%2080%25%20is%20considered%20healthy)
строить систему так, чтобы держать cache hit выше 80%.
Тогда возьмем худший сценарий и допустим cache miss 20%.

Из ДЗ 3 имеем: CDN забирает тяжелый медиа-трафик, но API-запросы ленты и поиска
все равно приходят в `feed-service` и `search-service`.

| Метрика       |              Всего |     Уходит на CDN media |    Остается на API |
| ------------- | -----------------: | ----------------------: | -----------------: |
| Average RPS   |         197 076.00 | media download отдельно |     **197 076.00** |
| Peak RPS      |         289 701.72 | media download отдельно |     **289 701.72** |
| Peak traffic  |        405.48 ГБ/с |             404.12 ГБ/с |      **1.36 ГБ/с** |
| Daily traffic | 23 273.43 ТБ/сутки |      23 195.58 ТБ/сутки | **77.85 ТБ/сутки** |

Будем считать что 20% трафика CDN ходит на origin ЦОДа, тогда:

| ------------- | -------------: | ----------------: | --------------------: |
| Average RPS   |     197 076.00 |          2 245.37 |        **199 321.37** |
| Peak RPS      |     289 701.72 |          3 300.69 |        **293 002.41** |
| Peak traffic  |      1.36 ГБ/с |        80.82 ГБ/с |        **82.18 ГБ/с** |
| Daily traffic | 77.85 ТБ/сутки | 4 639.12 ТБ/сутки | **4 716.97 ТБ/сутки** |

Всего у нас 3 ДЦ, но мы хотим позволить себе потерять один ДЦ

- Тогда каждый ДЦ должен держать 1/2 от общего трафика

| Метрика       | Итого на API в 1 ДЦ | Итого на origin в 1 ДЦ | Итого на API/origin в 1 ДЦ |
| ------------- | ------------------: | ---------------------: | -------------------------: |
| Average RPS   |           98 538.00 |               1 122.69 |              **99 660.69** |

| Peak traffic  |           0.68 ГБ/с |             40.41 ГБ/с |             **41.09 ГБ/с** |
| Daily traffic |      38.93 ТБ/сутки |      2 319.56 ТБ/сутки |      **2 358.49 ТБ/сутки** |

Итак

- Трафик приходит через BGP в конкретный датацентр
- То есть, на VIP нашего ЦОД пускают нагрузку `100-147к RPS` и 41.09 ГБ/с = `328.72 Гбит/с`

- разделим трафик c `api.vk.ru` и `media.vk.ru` по разным VIP
- `api.vk.ru` - api запросы (авторизация, лайки, комментарии и т.д.)
- `media.vk.ru` - CDN origin (картинки, видео)

## L3

- Трафик попадает в наш ДЦ через один из аплинков на один из edge роутеров.
  Запрос идет на VIP нашего ЦОДа, анонсированый LVS L4 балансировщиками
- Затем эти роутеры используют механизм ECMP: по хешу five tuple определяют LVS балансировщик

## L4

### Принцип

- Трафик попадает на L4 LVS балансировщик, который мы анонсировали VIP ЦОДа в Anycast и
  распределили через BGP, и выбрали конкретный LVS через ECMP
- Затем мы используем Direct Routing (подменяем MAC-адрес назначения на адрес одного из L7 балансировщиков)
  (чтобы избежать лишнего обратного трафика от LVS к клиенту и не нагружать bandwidth jn )
- Балансируем на L7 по Least Connections (тк у нас есть чатик, который долго держит соединение открытым)

### Число

Производительность LVS балансировщиков упирается в железо и пропускную способность сети.

- На один LVS я бы заложил 50к RPS и сетевые интерфейсы не ниже `2 × 100G`.
  Тогда нам нужно 3 LVS для 147к RPS и 329 Гбит/с в пике.
  И еще +1 для active-active резервирования, итого:
- 4 LVS на ЦОД

## L7

Имеем два кластера L7 балансировщиков: для `api.vk.ru` и для `media.vk.ru`.

### Принцип

- Трафик попадает на L7 балансировщик Nginx на баре метал машинке, MAC адрес которой мы подстивили на LVS машине
- На L7 балансировщике мы терминируем TLS
- И делаем rate limiting по IP
- После этого используем для распределения трафика между API серверами (в зависимости от типа сервиса)
- Используем Round Robin для быстрых запросов (например на сервисы авторизации)
- Используем Least Connections для медленных запросов (например чатик или загрузка медиа)

### L7 для `api.vk.ru`

На один Nginx я бы заложил 25к RPS. Тогда нам нужно 6 Nginx для 150к > 145к RPS в пике.
И еще +1 для active-active резервирования, итого:

- Round Robin
- 7 Nginx

### L7 для `media.vk.ru`

На один Nginx я бы заложил 60 Гбит/с и сетевые интерфейсы не ниже `100G`.
Тогда нам нужно 6 Nginx для 329 Гбит/с в пике.
И еще +1 для active-active резервирования, итого:

- Least Connections
- 7 Nginx

# Итого на ЦОД:

- 4 LVS
- 14 Nginx
