## 11.2 Модель развёртывания

Stateless-микросервисы разворачиваются в Kubernetes.
Stateful-компоненты и балансировщики разворачиваются на выделенных
bare-metal серверах.

Причина: им важны диски, сеть, предсказуемая задержка и отсутствие
накладных расходов контейнерной сети.

Для media-потока Kubernetes не находится в пути передачи больших файлов.
`media-service` отвечает за авторизацию загрузки, метаданные и выдачу ссылок.

Bulk traffic идет через Nginx media, SeaweedFS origin и SeaweedFS CDN cache.
Иначе 300+ Гбит/с origin-трафика пришлось бы тащить через pod-сеть.

`SeaweedFS origin` - durable object storage в основных ДЦ и source of truth
для файлов.

`SeaweedFS CDN cache` - отдельный кеширующий слой в CDN POP.
Он не является source of truth и может быть очищен или пересобран из origin.

| Компонент                                       | Модель развёртывания | Обоснование                                           |
| ----------------------------------------------- | -------------------- | ----------------------------------------------------- |
| `api-gateway`, доменные сервисы, worker-сервисы | Kubernetes           | Stateless, удобно горизонтально масштабировать        |
| LVS                                             | Bare-metal           | L4-балансировка, высокая сетевая нагрузка             |
| Nginx                                           | Bare-metal           | TLS termination, L7 routing, высокая сетевая нагрузка |
| PostgreSQL                                      | Bare-metal           | Stateful, строгая консистентность, Patroni            |
| ScyllaDB                                        | Bare-metal           | Stateful, высокая запись/чтение, локальные NVMe       |
| Redis                                           | Bare-metal           | In-memory cache, важна предсказуемость RAM            |
| Kafka                                           | Bare-metal           | Stateful broker, важны диски и сеть                   |
| OpenSearch                                      | Bare-metal           | Индексы поиска, локальные диски                       |
| SeaweedFS origin                                | Bare-metal           | Объектное хранилище, большие HDD-пулы                 |
| SeaweedFS CDN cache                             | Bare-metal           | CDN-кеш медиа и популярных объектов                   |
| CI/CD и временные окружения                     | OPEX                 | Нагрузка нерегулярная, важна эластичность             |

## 11.4 Ресурсные требования сервисов

Расчёт выполняется для одного ДЦ, который держит 50% мирового пика.

Исключение - PostgreSQL: запись по архитектуре идет в primary DC `MSK`.
Поэтому его серверы считаются как глобальная HA-топология, а не как одинаковый
набор узлов в каждом ДЦ.

Для файлового хранилища стартовый расчёт сделан под один год прироста:
11,56 ПБ логических данных по проекту.

Репликация `RF=3` трактуется как меж-ДЦ репликация: по одной полной копии
в каждом из трех ДЦ. Значит суммарно нужно 34,68 ПБ raw, а на один ДЦ
приходится 11,56 ПБ raw.

Один storage-capacity сервер даёт 96 ТБ raw. Для каждой полной копии нужно
`ceil(11 560 / 96) = 121` узел.

Итого на три ДЦ нужно `121 * 3 = 363` origin volume-узла.

ScyllaDB ограничена не CPU, а дисками. Логический объём Scylla-таблиц из ДЗ 5
с учётом денормализованных read-model из ДЗ 6 составляет порядка 120-130 ТБ.

Для social keyspace используется shared multi-DC модель: RF=1 в каждом ДЦ,
суммарно RF=3, строгие операции идут с `QUORUM`.

Для messenger keyspace family используется `home_dc` диалога: сообщения,
участники и inbox пишутся в `messenger_msk`, `messenger_spb` или
`messenger_ekb` с RF=3 и `LOCAL_QUORUM` внутри домашнего ДЦ. Асинхронные копии
в другие ДЦ создаются для failover и не находятся в синхронном пути отправки
сообщения.

Social keyspace даёт около 200-220 ТБ raw. Messenger keyspace с локальным RF=3
и асинхронными меж-ДЦ копиями даёт ещё около 270-290 ТБ raw. Суммарно для
Scylla нужно около 500 ТБ raw на кластер. Один `scylla`-узел даёт 3,84 ТБ raw,
поэтому берём `ceil(500 / 3,84) = 131` узел и резерв до 138 узлов. Для
симметричного размещения это 46 узлов на ДЦ.

Для CDN cache берём 5 точек из ДЗ 3: Москва, Волгоград, Екатеринбург,
Новосибирск, Хабаровск.

При равномерном распределении получается `3 232,96 / 5 = 646,6 Гбит/с`
на POP. Один cache-узел держит 60 Гбит/с.

Нужно `ceil(646,6 / 60) = 11` узлов и ещё 1 резервный узел на POP.
Итого: `12 * 5 = 60` CDN cache-узлов.

## 11.7 Конфигурации серверов и стоимость

Цены OPEX взяты из таблицы Selectel Dedicated, добавленной в этот раздел.

Цены покупки - оценка единовременной закупки собственного bare-metal сервера
близкой конфигурации, нормализованная по тем же классам серверов Selectel
и публичным ценам похожего железа из раздела источников. Это не точный BOM
от одного поставщика, а бюджетная оценка: публичные прайсы сильно зависят
от состояния сервера, гарантии, дисков, сетевых карт, НДС, доставки,
партии закупки и доступности конкретной конфигурации.

Амортизация покупки считается на 5 лет.

Термины:

- `CAPEX` - капитальные затраты, то есть разовая покупка серверов.
- `OPEX` - операционные затраты, то есть регулярные платежи за аренду.

Формулы:

```text
Покупка за 5 лет = Цена покупки * Количество
Амортизация/мес = Покупка за 5 лет / 60
OPEX за 5 лет = OPEX/мес * 60 * Количество
Окупаемость = Цена покупки / OPEX/мес
```

## 11.9 Что держать в CAPEX, а что в OPEX

Главная развилка: проект крупный, нагрузка стабильная и хорошо прогнозируемая.
Поэтому почти всю основную инфраструктуру выгоднее покупать.

OPEX-модель нужна там, где важна эластичность или нагрузка нерегулярная.
