# 7. Алгоритмы

## Гибридная генерация ленты

Лента пользователя генерируется заранее и читается из готовой read-model.
Для обычных сообществ используется fanout-on-write: при публикации пост сразу
раскладывается в ленты подписчиков. Для больших сообществ используется отложенная
генерация cron-воркерами: посты батчами попадают в ленты подписчиков и в региональные
рекомендации.

### Компоненты

| Компонент                | Назначение                                                               |
| :----------------------- | :----------------------------------------------------------------------- |
| `post-service`           | Сохраняет пост и событие `post.created`                                  |
| `outbox-relay`           | Перекладывает события из `event_outbox` в Kafka                          |
| `feed-worker`            | Обрабатывает события обычных сообществ и обновляет ленты                 |
| `feed-generator-cronjob` | Периодически генерирует задачи для больших сообществ и популярных постов |
| `feed-service`           | Читает персональную или fallback-ленту                                   |
| Redis                    | Локальный кеш первых страниц ленты внутри ДЦ                             |
| ScyllaDB                 | Source of truth для read-model ленты                                     |

### Данные

| Данные                        | Использование                                   |
| :---------------------------- | :---------------------------------------------- |
| `posts`                       | Канонический пост                               |
| `community_members`           | Список подписчиков сообщества                   |
| `user_feed_items`             | Персональная лента пользователя                 |
| `popular_feed_items`          | Популярная лента по региону                     |
| `users.home_region`           | Регион пользователя и выбор домашнего ДЦ        |
| Redis `feed:{user_id}`        | Кеш первых страниц персональной ленты           |
| Redis `popular_feed:{region}` | Кеш региональной fallback-ленты                 |
| Kafka `post.events`           | События публикации, изменения и удаления постов |
| Kafka `feed.generate`         | Задачи на батчевую генерацию ленты              |

### Публикация поста обычного сообщества

1. `post-service` записывает пост в `posts`.
2. В той же операции создается запись `post.created` в `event_outbox`.
3. `outbox-relay` публикует событие в Kafka topic `post.events`.
4. `feed-worker` читает событие и получает подписчиков сообщества из `community_members`.
5. Для каждого подписчика создается или обновляется запись в `user_feed_items`.
6. Запись выполняется по ключу `(user_id, published_at, post_id)`, поэтому повторная обработка события идемпотентна.
7. Если подписчик обслуживается в текущем ДЦ, `feed-worker` обновляет Redis `feed:{user_id}`.

### Публикация поста большого сообщества

Большим считается сообщество, для которого синхронный fanout создает слишком большой
всплеск записи в `user_feed_items`. Для таких сообществ пост не раскладывается сразу
по всем подписчикам.

1. `post-service` сохраняет пост и событие `post.created`.
2. `feed-worker` помечает пост как требующий батчевой генерации.
3. `feed-generator-cronjob` каждые 1-5 минут выбирает новые посты больших сообществ.
4. Cronjob делит подписчиков на батчи и публикует задачи в Kafka topic `feed.generate`.
5. `feed-worker` читает `feed.generate` и батчами записывает карточки в `user_feed_items`.
6. Для активных пользователей текущего ДЦ дополнительно прогревается Redis `feed:{user_id}`.
7. Если пост набирает высокий score, он также попадает в `popular_feed_items` нужного региона.

### Генерация региональной популярной ленты

1. `feed-generator-cronjob` периодически выбирает новые и активные посты.
2. Для каждого поста рассчитывается `score`.
3. Посты группируются по региону аудитории.
4. Лучшие посты записываются в `popular_feed_items` по ключу `(feed_region, score_bucket, score, post_id)`.
5. Redis `popular_feed:{region}` обновляется во всех ДЦ.

Формула score:

```text
score = reactions_count * 1.0 + comments_count * 2.0 - age_hours * 0.1
```

Score нужен только для порядка в популярной ленте. Персональная лента сортируется
по `published_at DESC`, а `score` используется как дополнительный сигнал.

### Чтение ленты

1. Пользователь направляется в ДЦ своего `home_region`.
2. `feed-service` читает Redis `feed:{user_id}`.
3. Если кеш найден, возвращаются первые посты ленты.
4. Если кеш пустой, `feed-service` читает `user_feed_items` из ScyllaDB и прогревает Redis.
5. Если персональная лента пустая или временно недоступна, возвращается Redis `popular_feed:{region}`.
6. Если Redis популярной ленты пустой, данные читаются из `popular_feed_items`.

### Падение ДЦ

1. Глобальная балансировка исключает упавший ДЦ.
2. Пользователи этого ДЦ переходят в один из здоровых ДЦ.
3. Пока персональный Redis-кеш не прогрет, `feed-service` отдает `popular_feed:{region}`.
4. `feed-generator-cronjob` создает задачи `feed.generate` на прогрев лент переехавших пользователей.
5. `feed-worker` восстанавливает Redis `feed:{user_id}` из `user_feed_items`.
6. После прогрева пользователь снова получает персональную ленту.

### Консистентность и ограничения

- `posts` - canonical source of truth для постов.
- `user_feed_items` и `popular_feed_items` - производные read-model.
- Redis не является source of truth и может быть восстановлен из ScyllaDB.
- Лента eventually consistent: новый пост может появиться с задержкой.
- Для больших сообществ задержка больше, потому что раскладка выполняется cron-воркерами.
- При повторной обработке событий дубли не создаются, так как ключ содержит `user_id`, `published_at`, `post_id`.
- Старые элементы ленты удаляются по `expires_at`.
